# AcquireIQ — Architecture and Deployment

This document describes the AcquireIQ system architecture and the deployment path used for the public portfolio instance.

Deployment is not required by the iAdeptive challenge. It is included because the existing project scaffold already contains a proven CI/CD and VPS deployment pattern, making a live deployment relatively inexpensive to retain. The public instance also provides a durable, working example of the completed application beyond the assessment itself.

Some deployment details below are specific to the existing cPanel/Apache VPS. They are operational notes for maintaining this deployment, not claims that this is the preferred production architecture for a government acquisition system.

---

# PART 1: ARCHITECTURE

---

## 1.1 System overview

```text
Browser
   |
   v
Apache / HTTPS
   |
   +-- /mvps/acquireiq/* ---------> React static build
   |
   +-- /mvps/acquireiq/api/* -----> AcquireIQ backend container
                                      |
                                      +----> PostgreSQL
                                      |
                                      +----> LLM provider
```

The browser never communicates directly with PostgreSQL or the LLM provider.

The React application communicates with the Node/Express API. Category routers handle endpoint-specific HTTP behavior, while backend services own acquisition business rules, workflow transitions, database access, dashboard aggregation, AI interpretation, and deterministic validation of AI-generated structured filters.

For AI-assisted search, the LLM interprets natural language and returns a structured filter. That filter returns to the API and is treated as untrusted input. Only after deterministic application validation may it influence a server-owned parameterized PostgreSQL query.

There is intentionally no direct LLM-to-database path.

## 1.2 Application request flow

Ordinary acquisition operations follow this path:

```text
React UI
   |
   | REST / JSON
   v
Node / Express API
   |
   | validation + business rules
   v
PostgreSQL
   |
   | result
   v
Node / Express API
   |
   | JSON
   v
React UI
```

AI-assisted search adds the LLM as an interpretation step:

```text
React AI Search
   |
   | natural-language request
   v
Node / Express API
   |
   | provider request
   v
LLM Provider
   |
   | untrusted structured filter
   v
Node / Express API
   |
   | schema + domain validation
   v
Validated internal filter
   |
   | parameterized SQL
   v
PostgreSQL
   |
   | matching requests
   v
Node / Express API
   |
   | results + confidence/fallback state
   v
React UI
```

This trust boundary is central to AcquireIQ. A model response being syntactically valid JSON does not make it valid application input.

## 1.3 Backend architecture

The backend is Node.js, Express, and TypeScript with `strict: true`.

TypeScript is the source language. Compiled JavaScript under `dist/` is the runtime artifact used by the production Docker container.

The backend follows the existing thin-router/service pattern:

```text
HTTP route
   |
   v
Request validation
   |
   v
Application/service logic
   |
   +----> PostgreSQL
   |
   +----> LLM provider integration
   |
   v
HTTP response
```

`server.ts` is the application composition root, responsible for global middleware, mounting the category routers, centralized error handling, and application startup.

The category routers own endpoint-specific HTTP behavior, including request parsing and validation, service invocation, HTTP status selection, and response formatting. 

Acquisition workflow logic, persistence behavior, status-transition rules, dashboard queries, and AI interpretation remain behind service boundaries.

This separation is useful beyond code organization. It keeps business logic independent of Express request/response objects and makes the important behavior easier to test.

AcquireIQ generates OpenAPI data schemas from TypeScript interfaces so the API models remain synchronized with the application types. Endpoint metadata remains explicit in swagger-spec.ts because routes, HTTP methods, parameters, response codes, and descriptions are HTTP concerns that cannot be inferred from those data types alone. The endpoint metadata could also be generated by introducing decorators or additional route-generation tooling, but for AcquireIQ's small API surface that additional framework complexity was not justified. This approach automates the portion most susceptible to type drift while keeping the HTTP contract straightforward and explicit.

`POST /requests` intentionally treats each successful submission as creation of a new acquisition resource, so identical payloads may produce separate records with different IDs. AcquireIQ does not enforce uniqueness across request fields because identical titles, requestors, budgets, or fiscal years do not necessarily represent the same business acquisition. In a production system where retry-driven duplicate creation is a concern, the API could add an idempotency key and the UI could prevent repeated submission while a request is pending. That additional mechanism is not included here because idempotent creation was not a challenge requirement and would add API and persistence complexity without an established business rule requiring it.

## 1.4 PostgreSQL architecture

PostgreSQL is the authoritative store for AcquireIQ state.

The required domain includes:

```text
users
acquisition_requests
vendors
contracts
approvals
protests
```

The database is responsible for durable relational state and participates directly in correctness through transactions, constraints, and indexes.

Parallel approvals are represented as separate approval records that may share the same `stage_sequence`. A request advances toward approval only after every required approver in the current stage has approved. A pending or rejected decision in the current stage blocks approval, while later-stage approvals do not affect completion of the current stage.

Status transitions are not treated as arbitrary CRUD updates. The application owns the valid transition graph, while PostgreSQL transaction/concurrency mechanisms protect the state used to make the transition decision.

The implemented PostgreSQL schema uses relational constraints and indexes for workflow integrity and common access patterns. Database setup uses the native `psql` bootstrap, demonstration data is loaded through the separate seed process, and concurrency-sensitive status transitions use transactions with `SELECT ... FOR UPDATE` row locking.

## 1.5 Concurrency boundary

The status-transition path is one of the highest-risk parts of the application.

The transition check and corresponding database update execute as one concurrency-safe operation within a PostgreSQL transaction. Two callers cannot both make transition decisions from the same stale request state and commit incompatible results.

Conceptually:

```text
Caller A ----\
              \
               >---- transaction / concurrency boundary ----> acquisition state
              /
Caller B ----/
```

The implemented strategy locks the acquisition request row with `SELECT ... FOR UPDATE` before validating its current state. Competing transitions against the same request are serialized, and a waiting transaction re-evaluates the committed state before proceeding.

## 1.6 AI provider boundary

The LLM integration is isolated from the acquisition-query logic.

Provider-specific request formatting, authentication, response extraction, and provider errors belong behind a small provider boundary. The rest of the application operates on an internal structured-filter contract.

The LLM is used for interpretation, not authorization or query execution.

Not allowed:

```text
Natural language
      |
      v
LLM-generated SQL
      |
      v
Database
```

AcquireIQ instead uses:

```text
Natural language
      |
      v
LLM
      |
      v
Structured filter
      |
      v
Application validation
      |
      v
Server-owned parameterized SQL
      |
      v
PostgreSQL
```

Hallucinated fields, unsupported values, malformed output, and other out-of-schema responses are rejected before database access.

The API exposes an explicit low-confidence or fallback condition when the interpretation cannot be trusted. The React UI will make that state visible as part of the completed frontend implementation.

## 1.7 Frontend architecture

The frontend uses React and Vite.

The existing scaffold provides a centralized API client, reusable component structure, logging, loading/error handling patterns, and a working backend health check.

AcquireIQ builds the acquisition-specific interface on that foundation.

Primary user-facing areas are expected to include:

```text
Acquisition pipeline
Acquisition request detail
Approval chain
Status actions
Dashboard
AI-assisted search
AI confidence/fallback state
Loading state
Error state
```

The frontend consumes the real backend API. Acquisition workflow rules remain server-owned rather than being enforced only by UI controls.

## 1.8 OpenAPI

The backend exposes Swagger/OpenAPI documentation through:

```text
/api/docs
```

AcquireIQ generates OpenAPI component schemas from exported TypeScript interfaces while route metadata remains explicitly maintained in `swagger-spec.ts`.

This reduces response-schema drift without requiring a larger framework change solely to generate every part of the OpenAPI document.

## 1.9 Why reuse the existing scaffold

AcquireIQ deliberately starts from a previously proven application scaffold rather than rebuilding generic infrastructure from scratch.

Reusable pieces include:

- React / Vite baseline
- Node / Express / TypeScript baseline
- strict TypeScript configuration
- health endpoint
- Swagger / OpenAPI support
- centralized logging
- Docker backend build
- CI workflow structure
- VPS deployment workflow structure
- Apache reverse-proxy pattern
- frontend static-build deployment

AcquireIQ-specific behavior is new:

- PostgreSQL acquisition model
- acquisition request APIs
- parallel approval workflow
- concurrency-safe status transitions
- dashboard aggregation
- AI structured-filter contract
- LLM-provider integration
- AI validation/fallback behavior
- AcquireIQ React interface
- AcquireIQ tests

Reusing infrastructure is an engineering decision, not an attempt to treat old application logic as part of this solution. The goal is to spend assessment time on the domain, concurrency, API, AI-reliability, and UI decisions that actually distinguish AcquireIQ.

# PART 2: PUBLIC DEPLOYMENT

---

## 2.1 Why deploy when the challenge does not require it

The iAdeptive challenge does not require production deployment or a publicly accessible instance.

AcquireIQ will nevertheless be deployed to the existing VPS because the deployment scaffolding already exists and the incremental cost is small compared with standing up deployment infrastructure from scratch. This is also a deliberate decision to go beyond the challenge requirements: AcquireIQ is intended to remain available after the assessment as another public showcase of the engineering work, rather than existing only as a repository created for an interview exercise.

The live deployment therefore serves two purposes:

1. It gives reviewers an optional working instance in addition to the repository.
2. It preserves AcquireIQ as a publicly accessible portfolio application demonstrating the completed architecture, backend, frontend, database, and AI integration.

The challenge suggests a focused implementation window, but the additional time spent beyond that window is intentional. Once the decision was made to retain AcquireIQ as a public portfolio application, stopping at an artificial time boundary and returning later to complete the same work would be inefficient while the architecture, implementation decisions, and codebase are already fresh.

Unfortunately, today's technology hiring market increasingly expects candidates to present exceptionally polished and complete work during the interview process. That incentive is different from normal product delivery. In a professional delivery environment, the objective is correctness, maintainability, fitness for purpose, and business value—not pursuing perfection beyond what the requirements and priorities justify.

The additional effort here is therefore a deliberate expansion of the project's purpose, not an inability to control scope. It is enabled by existing infrastructure and is not a dependency of the challenge implementation.

The repository remains the authoritative assessment deliverable.

## 2.2 Public URL layout

The intended public path is:

```text
https://leelinkoff.com/mvps/acquireiq/
```

The frontend is served below:

```text
/mvps/acquireiq/
```

API traffic is routed below:

```text
/mvps/acquireiq/api/
```

The API prefix is intentionally application-specific. Multiple applications share the same Apache server, so AcquireIQ must not claim a generic domain-root `/api/` route that could collide with another deployed application.

## 2.3 VPS layout

The deployment follows the existing separation between source/build staging, the backend runtime container, and Apache's public static directory.

Planned layout:

```text
/opt/acquireiq/
|
+-- backend/
+-- frontend/
    |
    +-- dist/        generated frontend build
```

The public static frontend is copied to:

```text
/home/leelinko/public_html/mvps/acquireiq/
```

The backend source under `/opt/acquireiq/backend/` is used to build a Docker image. The running backend is a container created from that image.

These are different things:

```text
backend/Dockerfile
      |
      | docker build
      v
AcquireIQ backend image
      |
      | docker run
      v
AcquireIQ backend container
```

The container is replaced during deployment rather than modified in place.

## 2.4 Why Docker is retained

The existing VPS does not have a usable native Node.js runtime. Previous deployment work on this server established that Node applications need to build and run inside containers rather than directly on the host.

AcquireIQ therefore retains Docker for the backend.

The frontend build can likewise run in a temporary Node container, after which only the generated static files need to be served by Apache.

For this server, Docker is therefore not merely a packaging preference. It isolates the application from the host's unusable Node environment and reuses an already-proven deployment mechanism.

## 2.5 Backend port

The AcquireIQ backend needs its own unused internal host port.

The exact port must be selected after checking the ports already allocated to applications on the VPS.

Do not assume that the old template's port is available.

Once selected, the container must bind only to loopback:

```text
127.0.0.1:<ACQUIREIQ_PORT>:<CONTAINER_PORT>
```

For example, if port `3003` is confirmed free and the application listens on `3003` inside the container:

```bash
docker run -d \
  --name acquireiq-backend \
  --restart unless-stopped \
  -p 127.0.0.1:3003:3003 \
  --env-file .env \
  acquireiq-backend
```

The explicit `127.0.0.1` binding matters.

This:

```text
-p 3003:3003
```

normally publishes the port on all host interfaces.

This:

```text
-p 127.0.0.1:3003:3003
```

restricts the published host port to loopback so normal public API traffic must pass through Apache.

The actual port will replace the placeholder/example after it is verified on the VPS.

## 2.6 Apache reverse proxy

Apache terminates public HTTPS and forwards AcquireIQ API requests to the loopback-bound backend container.

The final rule should have this shape:

```apache
<IfModule mod_proxy.c>
    ProxyPreserveHost On
    ProxyPass "/mvps/acquireiq/api/" "http://127.0.0.1:<ACQUIREIQ_PORT>/api/"
    ProxyPassReverse "/mvps/acquireiq/api/" "http://127.0.0.1:<ACQUIREIQ_PORT>/api/"
</IfModule>
```

`<ACQUIREIQ_PORT>` must be replaced with the verified port before the configuration is installed.

On this VPS, the existing Apache include used for application proxy rules is:

```text
/etc/apache2/conf.d/includes/post_virtualhost_global.conf
```

Because this is a shared Apache instance, always validate configuration before applying it:

```bash
apachectl -t
```

On this cPanel/EasyApache server, the previously verified reload mechanism is:

```bash
/usr/local/cpanel/scripts/restartsrv_httpd --graceful
```

That cPanel-specific behavior is retained because it was learned from direct operation of this server. It is not intended as generic Apache deployment guidance.

## 2.7 Frontend base path

AcquireIQ is hosted below a subpath rather than at the domain root.

The frontend must therefore be built so asset paths and API paths work correctly below:

```text
/mvps/acquireiq/
```

The API client should derive the deployed API location from application/base configuration rather than hardcoding a domain-root `/api/` assumption.

Local development and production should resolve to the same backend API contract even though the transport routing differs:

```text
Local development
React/Vite -> local API or Vite proxy -> Express

Production
Browser -> /mvps/acquireiq/api/* -> Apache -> Express container
```

The exact Vite base/proxy configuration will be documented after it is implemented and tested.

## 2.8 PostgreSQL deployment

AcquireIQ introduces a persistent database requirement that the original generic scaffold did not provide.

The final deployment must define:

```text
PostgreSQL host
database name
application database user
connection configuration
migration procedure
seed procedure for the demo dataset
backup/recovery expectations for the public demo
```

Credentials must be supplied through server-side configuration and must never be exposed through frontend `VITE_*` variables.

The exact PostgreSQL hosting arrangement is intentionally not invented in this document. It will be recorded after the database is provisioned and verified on the deployment environment.

## 2.9 LLM configuration

The backend, not the browser, owns the LLM API credential.

AcquireIQ uses OpenAI as its implemented LLM provider. The backend receives the provider credential through `OPENAI_API_KEY`, while `OPENAI_MODEL` optionally selects the model and defaults to `gpt-5.4-mini`.

The frontend must never receive the provider secret.

Conceptually:

```text
Browser
   |
   v
AcquireIQ API
   |
   +---- server-side credential ----> LLM provider
```

These credentials and configuration values remain backend-only and are never exposed through frontend `VITE_*` environment variables.

## 2.10 CI/CD

The repository retains the existing GitHub Actions deployment pattern.

The intended pipeline is:

```text
Push to main
     |
     v
Verify build
     |
     +-- backend dependencies
     +-- generated schemas
     +-- TypeScript check/build
     +-- frontend dependencies
     +-- frontend build
     +-- tests/checks
     |
     v
Deploy
     |
     +-- sync source to VPS staging path
     +-- write server-side environment
     +-- build backend Docker image
     +-- replace backend container
     +-- run frontend build
     +-- publish frontend dist
     +-- run public health check
```

Deployment must not proceed if verification fails.

The existing workflow is scaffolding, not evidence that AcquireIQ deployment already works. Application names, paths, ports, environment variables, health URLs, and any old project-specific references must be changed and tested before the workflow is considered valid for AcquireIQ.

## 2.11 Local workflow testing

The scaffold includes local workflow-testing support using `act`, plus pre-commit checks for workflow and shell syntax.

Those tools remain useful because AcquireIQ is reusing the deployment pipeline shape.

The important distinction is that local validation of the workflow does not prove the live deployment works. Public routing, VPS paths, Docker networking, environment configuration, PostgreSQL connectivity, and the final health endpoint must still be tested against the actual server.

## 2.12 Manual deployment fallback

After the AcquireIQ-specific values are finalized, the automated deployment can be reproduced manually for debugging.

Conceptually:

```bash
cd /opt/acquireiq/backend

docker build -t acquireiq-backend .

docker rm -f acquireiq-backend || true

docker run -d \
  --name acquireiq-backend \
  --restart unless-stopped \
  -p 127.0.0.1:<ACQUIREIQ_PORT>:<CONTAINER_PORT> \
  --env-file .env \
  acquireiq-backend
```

Frontend build:

```bash
docker run --rm \
  -v "/opt/acquireiq/frontend:/app" \
  -w /app \
  node:20-alpine sh -c "npm install && npm run build"

rsync -a --delete \
  "/opt/acquireiq/frontend/dist/" \
  "/home/leelinko/public_html/mvps/acquireiq/"
```

Public verification:

```bash
curl -f https://leelinkoff.com/mvps/acquireiq/api/health
```

Placeholders in these commands must be replaced with the implemented backend port before use.

## 2.13 Deployment verification

A successful process exit is not sufficient evidence of a successful deployment.

The deployment should verify each meaningful boundary:

```text
Backend container is running
        |
        v
Backend responds on loopback
        |
        v
PostgreSQL connectivity works
        |
        v
Apache configuration is valid
        |
        v
Public health endpoint responds
        |
        v
Frontend loads from public path
        |
        v
Frontend can call public API
        |
        v
Core acquisition read/write flow works
        |
        v
AI-assisted query works or exposes its intended fallback
```

This distinguishes "the deploy command completed" from "the application is actually usable."

## 2.14 Security notes for the public demo

The challenge permits authentication and deployment to be skipped, so the public portfolio deployment should not be mistaken for a production government system.

At minimum:

- backend host ports should bind only to `127.0.0.1`
- PostgreSQL should not be publicly exposed
- database credentials and LLM credentials remain server-side
- secrets are excluded from source control
- `VITE_*` variables must never contain secrets
- SQL must remain server-owned and parameterized
- LLM output must remain validated before database access
- demo/seed data should contain no real sensitive acquisition information
- CORS should be no broader than necessary for the deployed frontend

Authentication is not required for the challenge. If the public instance permits mutations without authentication, that limitation must be considered explicitly before leaving it publicly writable.

A practical portfolio deployment may expose read/demo behavior while restricting, resetting, or otherwise controlling mutations. The final choice should be documented after the live behavior is decided.

## 2.15 What would change for a real production system

The VPS deployment is appropriate for a portfolio demonstration because the infrastructure already exists and the application is small.

It is not presented as the target architecture for a real government contracting office.

A production system would require additional decisions around:

```text
identity and authorization
auditability
secrets management
managed database availability
backup and recovery
observability
network isolation
rate limiting
data retention
security review
accessibility verification
deployment environments
rollback strategy
LLM governance and monitoring
```

Those concerns are deliberately separated from the challenge implementation so the prototype can remain focused on the requested engineering problem.
