# AcquireIQ — Architecture and Deployment

This document describes the AcquireIQ system architecture and its optional public deployment.

Deployment is not required by the challenge. AcquireIQ has two deployment paths: a VPS deployment, the planned primary, run by `deploy-to-vps.yml`; and an optional AWS deployment, defined as Terraform in `infra/` and run by `deploy-to-aws.yml`. Neither has yet been run against a live environment.

The deployment described here is a demonstration deployment. It is not presented as the preferred production architecture for a government acquisition system.

---

# PART 1: ARCHITECTURE

---

## 1.1 System overview

```text
Browser
   |
   v
HTTPS entry point (Apache on the VPS, or CloudFront on AWS)
   |
   +-- /acquireiq/* ---------------------------> React static build
   |
   +-- /api/*  /requests*  /dashboard*  /assist/*
          |
          v
       AcquireIQ backend container (port 3002)
          |
          +----> PostgreSQL
          |
          +----> LLM provider
```

The React build calls the API on the same origin. On the VPS, every path above sits under `/mvps/acquireiq`; on AWS the frontend is served at `/acquireiq/` and the API paths at the root. In local development the Vite dev server proxies the same API paths to the backend on `localhost:3002`.

The browser never communicates directly with PostgreSQL or the LLM provider.

The React application communicates with the Node/Express API. Category routers handle endpoint-specific HTTP behavior, while backend services own acquisition workflow orchestration, request-status business rules, database access, dashboard aggregation, AI interpretation, and deterministic validation of AI-generated structured search filters. PostgreSQL owns authoritative approval-stage derivation and persistent enforcement of current-stage approval-decision integrity.

For AI-assisted search, the LLM interprets natural language and returns a structured filter. That filter returns to the API and is treated as untrusted input. Only after deterministic application validation may it influence a server-owned parameterized PostgreSQL query.

There is intentionally no direct LLM-to-database path.

## 1.2 Application request flow

Ordinary acquisition operations follow this path:

```text
React UI
   |
   | REST / JSON
   v
Node / Express API
   |
   | HTTP validation + workflow orchestration
   v
PostgreSQL
   |
   | persistence + database-enforced integrity
   v
Node / Express API
   |
   | result mapping + JSON
   v
React UI
```

AI-assisted search adds the LLM as an interpretation step:

```text
React AI Search
   |
   | natural-language request
   v
Node / Express API
   |
   | provider request
   v
LLM Provider
   |
   | untrusted structured filter
   v
Node / Express API
   |
   | schema + domain validation
   v
Validated internal filter
   |
   | parameterized SQL
   v
PostgreSQL
   |
   | matching requests
   v
Node / Express API
   |
   | results + confidence/fallback state
   v
React UI
```

This trust boundary is central to AcquireIQ. A model response being syntactically valid JSON does not make it valid application input.

## 1.3 Backend architecture

The backend is Node.js, Express, and TypeScript with `strict: true`.

TypeScript is the source language. Compiled JavaScript under `dist/` is the runtime artifact used by the production Docker container.

The backend follows the existing thin-router/service pattern:

```text
HTTP route
   |
   v
Request validation
   |
   v
Application/service logic
   |
   +----> PostgreSQL
   |
   +----> LLM provider integration
   |
   v
HTTP response
```

`server.ts` is the application composition root, responsible for global middleware, mounting the category routers, centralized error handling, and application startup.

The category routers own endpoint-specific HTTP behavior, including request parsing and validation, service invocation, HTTP status selection, and response formatting. 

Acquisition workflow orchestration, persistence access, request-status transition rules, dashboard queries, and AI interpretation remain behind service boundaries. For approval decisions, the backend service invokes PostgreSQL's authoritative approval operation, interprets its result, and exposes PostgreSQL-derived current-stage and stage-state information through the API.

This separation is useful beyond code organization. It keeps business logic independent of Express request/response objects and makes the important behavior easier to test.

AcquireIQ generates OpenAPI data schemas from TypeScript interfaces so the API models remain synchronized with the application types. Endpoint metadata remains explicit in swagger-spec.ts because routes, HTTP methods, parameters, response codes, and descriptions are HTTP concerns that cannot be inferred from those data types alone. The endpoint metadata could also be generated by introducing decorators or additional route-generation tooling, but for AcquireIQ's small API surface that additional framework complexity was not justified. This approach automates the portion most susceptible to type drift while keeping the HTTP contract straightforward and explicit.

`POST /requests` intentionally treats each successful submission as creation of a new acquisition resource, so identical payloads may produce separate records with different IDs. AcquireIQ does not enforce uniqueness across request fields because identical titles, requestors, budgets, or fiscal years do not necessarily represent the same business acquisition. In a production system where retry-driven duplicate creation is a concern, the API could add an idempotency key and the UI could prevent repeated submission while a request is pending. That additional mechanism is not included here because idempotent creation was not a challenge requirement and would add API and persistence complexity without an established business rule requiring it.

## 1.4 PostgreSQL architecture

PostgreSQL is the authoritative store for AcquireIQ state.

The required domain includes:

```text
users
acquisition_requests
vendors
contracts
approvals
protests
```

The database is responsible for durable relational state and participates directly in correctness through transactions, constraints, and indexes.

Parallel approvals are represented as separate approval records that may share the same `stage_sequence`. This allows multiple approvers to participate independently within the same approval stage. PostgreSQL derives each stage as `future`, `current`, or `complete` from the authoritative approval records. Approval decisions are recorded only when the specified approval is still pending and belongs to the current approval stage, with that rule enforced at the PostgreSQL write boundary. Once every approver at the current stage has recorded a decision, the next incomplete stage becomes current through derived state rather than a separately persisted progression value. AcquireIQ deliberately does not infer broader business rules the challenge does not define, including special consequences for rejected or mixed decisions or any relationship between approval-stage progression and acquisition-request status.

Status transitions are not treated as arbitrary CRUD updates. The application owns the valid transition graph, while PostgreSQL transaction/concurrency mechanisms protect the state used to make the transition decision.

The implemented PostgreSQL schema uses relational constraints and indexes for workflow integrity and common access patterns. Database setup uses the native `psql` bootstrap, demonstration data is loaded through the separate seed process, and concurrency-sensitive status transitions use transactions with `SELECT ... FOR UPDATE` row locking.

## 1.5 Concurrency boundary

The status-transition path is one of the highest-risk parts of the application.

The transition check and corresponding database update execute as one concurrency-safe operation within a PostgreSQL transaction. Two callers cannot both make transition decisions from the same stale request state and commit incompatible results.

Conceptually:

```text
Caller A ----\
              \
               >---- transaction / concurrency boundary ----> acquisition state
              /
Caller B ----/
```

The implemented strategy locks the acquisition request row with `SELECT ... FOR UPDATE` before validating its current state. Competing transitions against the same request are serialized, and a waiting transaction re-evaluates the committed state before proceeding.

## 1.6 AI provider boundary

The LLM integration is isolated from the acquisition-query logic.

Provider-specific request formatting, authentication, response extraction, and provider errors belong behind a small provider boundary. The rest of the application operates on an internal structured-filter contract.

The LLM is used for interpretation, not authorization or query execution.

Not allowed:

```text
Natural language
      |
      v
LLM-generated SQL
      |
      v
Database
```

AcquireIQ instead uses:

```text
Natural language
      |
      v
LLM
      |
      v
Structured filter
      |
      v
Application validation
      |
      v
Server-owned parameterized SQL
      |
      v
PostgreSQL
```

Hallucinated fields, unsupported values, malformed output, and other out-of-schema responses are rejected before database access.

The API exposes an explicit low-confidence or fallback condition when the interpretation cannot be trusted. The React UI makes that state visibly distinct from a normal successful AI-assisted result.

## 1.7 Frontend architecture

The frontend uses React and Vite.

The reusable frontend scaffold deliberately uses JavaScript rather than TypeScript. Because the frontend is intentionally a relatively thin presentation and interaction layer, with consequential business rules and workflow validation remaining backend-owned, the additional compile-time type layer and build/debugging indirection of TypeScript were not considered justified for this UI. Using JavaScript keeps the browser-facing implementation closer to the language ultimately executed by the browser and reduces unnecessary complexity during development and debugging. If the frontend evolved to contain substantially richer client-side domain logic, state, or shared contracts, the tradeoff would change and TypeScript would become a stronger choice.

The existing scaffold provides a centralized API client, reusable component structure, logging, loading/error handling patterns, and a working backend health check.

AcquireIQ builds the acquisition-specific interface on that foundation.

Primary user-facing areas include:

```text
Acquisition pipeline
Acquisition request detail
Approval chain and derived stage state
Approval decision actions
Request-status actions
Dashboard
AI-assisted search
AI confidence/fallback state
Loading state
Error state
```

The frontend consumes the real backend API. Acquisition workflow rules remain server-owned rather than being enforced only by UI controls.

## 1.8 OpenAPI

The backend exposes Swagger/OpenAPI documentation through:

```text
/api/docs
```

AcquireIQ generates OpenAPI component schemas from exported TypeScript interfaces while route metadata remains explicitly maintained in `swagger-spec.ts`.

This reduces response-schema drift without requiring a larger framework change solely to generate every part of the OpenAPI document.

## 1.9 Why reuse the existing scaffold

AcquireIQ deliberately starts from a previously proven application scaffold rather than rebuilding generic infrastructure from scratch.

Reusable pieces include:

- React / Vite baseline
- Node / Express / TypeScript baseline
- strict TypeScript configuration
- health endpoint
- Swagger / OpenAPI support
- centralized logging
- Docker backend build
- CI workflow structure
- VPS deployment workflow structure
- Apache reverse-proxy pattern
- frontend static-build deployment

AcquireIQ-specific behavior is new:

- PostgreSQL acquisition model
- acquisition request APIs
- parallel approval modeling, PostgreSQL-enforced decision recording and stage-state derivation, and backend API orchestration
- concurrency-safe status transitions
- dashboard aggregation
- AI structured-filter contract
- LLM-provider integration
- AI validation/fallback behavior
- AcquireIQ React interface
- AcquireIQ tests

Reusing infrastructure is an engineering decision, not an attempt to treat old application logic as part of this solution. The goal is to spend assessment time on the domain, concurrency, API, AI-reliability, and UI decisions that actually distinguish AcquireIQ.

# PART 2: PUBLIC DEPLOYMENT

## 2.1 Why deploy when the challenge does not require it

The challenge does not require production deployment or a publicly accessible instance.

AcquireIQ nevertheless includes a deployment path. This is a deliberate decision to go beyond the challenge requirements: AcquireIQ is intended to remain available after the assessment as another public showcase of the engineering work, rather than existing only as a repository created for an interview exercise.

A live deployment therefore serves two purposes:

1. It gives reviewers an optional working instance in addition to the repository.
2. It preserves AcquireIQ as a publicly accessible portfolio application demonstrating the completed architecture, backend, frontend, database, and AI integration.

The challenge suggests a focused implementation window, but the additional time spent beyond that window is intentional. Once the decision was made to retain AcquireIQ as a public portfolio application, stopping at an artificial time boundary and returning later to complete the same work would be inefficient while the architecture, implementation decisions, and codebase are already fresh.

The additional effort is a deliberate expansion of the project's purpose, not a dependency of the challenge implementation. I chose to invest additional time because I believe the resulting application is well engineered and worth retaining as a polished project that I can revisit, critically review, learn from, and continue to evolve after the assessment.

The repository remains the authoritative assessment deliverable.

## 2.3 AWS architecture

```text
Browser
   |  HTTPS
   v
CloudFront
   |-- /acquireiq/*                          --> S3 bucket (React build, private)
   |-- /api/*  /requests*  /dashboard*  /assist/*
          |
          v
   Application Load Balancer (public subnets)
          |
          v
   ECS Fargate task running the backend image (port 3002)
          |
          +--> RDS PostgreSQL 17 (private subnets)
          +--> OpenAI API
```

Key points:

- **One public address.** CloudFront serves the frontend and forwards the API paths to the load balancer, so the browser calls the API on the same origin and no CORS or mixed-content handling is needed.
- **Network.** A dedicated VPC (`10.20.0.0/16`) across two Availability Zones. Public subnets hold the load balancer and, by default, the API task. Private subnets hold the database. An optional NAT gateway (`use_nat_gateway = true`) moves the API task into the private subnets.
- **Security groups.** The load balancer accepts traffic only from CloudFront, the API task only from the load balancer, and the database only from the API and db-init tasks.
- **Secrets.** `DATABASE_URL`, `OPENAI_API_KEY` and the database passwords are stored in AWS Secrets Manager and injected into the containers at start. None are stored in the image, the task definition, or a `VITE_*` variable.
- **Database setup.** A one-off `db-init` ECS task creates the `acquireiq_app` role with the deployment password and runs `backend/scripts/setup-database.sql` inside the VPC. Seed data is not loaded automatically.
- **Health and recovery.** The load balancer checks `/api/health` every 30 seconds. Two consecutive failures mark the task unhealthy, and ECS replaces it.
- **Logs.** Backend and db-init container output goes to CloudWatch Logs.

The AWS deployment uses the backend Docker image built from `backend/Dockerfile`, the same image used for local Docker builds.

## 2.4 AWS CI/CD

A one-time bootstrap (`infra/bootstrap/main.tf`, run from a workstation) creates the Terraform state bucket, the ECR repositories, and a GitHub OIDC deploy role, so the workflow needs no stored AWS keys.

`deploy-to-aws.yml` is started manually from the GitHub Actions tab:

```text
Run workflow
     |
     +-- log in to AWS through GitHub OIDC
     +-- build and push the backend and db-init images
     +-- terraform apply
     +-- run the db-init task, fail the deploy if it fails
     +-- wait for the API service to become stable
     +-- build the frontend, upload it to S3, clear the CloudFront cache
     +-- check /api/health through CloudFront
```

Required repository secrets: `AWS_ROLE_ARN`, `TF_STATE_BUCKET`, `DB_MASTER_PASSWORD`, `DB_APP_PASSWORD`, `OPENAI_API_KEY`.

`code-checks.yml` runs separately on every push and pull request to `main`: frontend build, strict TypeScript check, and a backend boot test against a disposable PostgreSQL container.

## 2.5 Local workflow testing

The repository includes local workflow-testing support using `act`, plus pre-commit checks for workflow and shell syntax.

Local validation of a workflow does not prove the live deployment works. Public routing, networking, environment configuration, PostgreSQL connectivity, and the final health endpoint must still be tested against the real environment.

## 2.6 Deployment verification

A successful process exit is not sufficient evidence of a successful deployment.

The deployment should verify each meaningful boundary:

```text
Backend container is running
        |
        v
PostgreSQL connectivity works
        |
        v
Public health endpoint responds
        |
        v
Frontend loads from public path
        |
        v
Frontend can call public API
        |
        v
Core acquisition read/write flow works
        |
        v
AI-assisted query works or exposes its intended fallback
```

`deploy-to-aws.yml` automates the container, database setup, and public health checks. The remaining steps are manual.

## 2.7 Security notes for the public demo

The challenge permits authentication and deployment to be skipped, so the public portfolio deployment should not be mistaken for a production government system.

Two major deficiencies are accepted for this demo:

1. **No API authentication.** Anyone with the URL can read, create, and change acquisition requests and record approvals.
2. **No rate limiting.** Anyone can send unlimited requests, including to `/assist/query`, which calls the LLM provider. A monthly spending limit should be set on the LLM provider account.

Both must be addressed before the deployment holds real data.

Controls that are in place:

- the API is reachable only through the load balancer on AWS, or through Apache with the container bound to `127.0.0.1` on the VPS
- PostgreSQL is in private subnets and is not publicly accessible
- database and LLM credentials remain server-side
- secrets are excluded from source control
- `VITE_*` variables never contain secrets
- SQL remains server-owned and parameterized
- LLM output is validated before database access
- demo and seed data contain no real sensitive acquisition information

## 2.8 VPS deployment

`deploy-to-vps.yml` deploys to a Linux server running Apache and Docker. It is the planned primary deployment and runs automatically on every push to `main`, or by hand from the GitHub Actions tab. Until the server is set up, runs stop at the secrets or SSH check before changing anything.

```text
Browser
   |  HTTPS
   v
Apache
   |-- /mvps/acquireiq/                               --> static React build
   |-- /mvps/acquireiq/api/  /requests  /dashboard  /assist/
          |
          v
   backend container, 127.0.0.1:3002 only
          |
          +--> PostgreSQL on the server (host.docker.internal)
          +--> OpenAI API
```

The workflow builds the frontend with `VITE_BASE_PATH=/mvps/acquireiq/` and `VITE_API_BASE=/mvps/acquireiq`, so assets and API calls stay under the application's path. It writes `backend/.env` from GitHub secrets on every run, rebuilds and restarts the backend container, publishes the static build, and checks the public health URL.

One-time server setup, not done by the workflow:

```text
Docker installed, usable by the SSH user
PostgreSQL installed, schema created with setup-database.sql,
  and accepting connections from Docker containers
Apache ProxyPass rules for the API paths (the workflow prints them
  and stops if they are missing)
static folder served by Apache at /mvps/acquireiq/
host port 3002 free
GitHub secrets set with dev_scripts\deploy_setup.bat
```

## 2.9 What would change for a real production system

The demonstration deployment is appropriate for a portfolio application because the application is small.

It is not presented as the target architecture for a real government contracting office.

A production system would require additional decisions around:

```text
identity and authorization
auditability
secrets management
managed database availability
backup and recovery
observability
network isolation
rate limiting
data retention
security review
accessibility verification
deployment environments
rollback strategy
LLM governance and monitoring
```

Those concerns are deliberately separated from the challenge implementation so the prototype can remain focused on the requested engineering problem.

## 3.2 Documentation rule

Deployment documentation should describe verified behavior.

Any port, path, provider, database arrangement, environment variable, or public URL that has not yet been tested should remain explicitly identified as planned or provisional.

That distinction keeps the repository useful both as an assessment submission and as long-term documentation for the public portfolio instance.
