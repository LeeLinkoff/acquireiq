AcquireIQ on AWS

How the app runs once infra/main.tf and infra/bootstrap/main.tf are applied: one HTTPS address in front, a private database behind, and a GitHub Actions workflow that builds and ships every release.

Design from the Terraform files. Not yet deployed or tested against AWS.
Two major deficiencies, accepted for this demo
  1. No API authentication. Anyone with the URL can read, create and change acquisition requests and record approvals.
  2. No rate limiting. Anyone can flood the API, including the search endpoint that calls OpenAI. Set a monthly spending limit on the OpenAI key.
Both must be added before this holds real data. Details are in the last section.

      Why some services sit outside the VPC

      The VPC is the app's private network. Only things that need their own IP address in it go inside. Everything else is a service AWS runs itself and the app calls over HTTPS.

      WhereServicesWhy there, and what controls access
      Inside the VPCLoad balancer, API task, db-init task, RDSEach gets an IP address in the app's subnets. Security groups and route tables decide who can reach them.
      Region, outside the VPCS3, ECR, Secrets Manager, CloudWatch Logs, IAMShared regional services run by AWS. They are not placed anywhere; the app calls them over HTTPS through the internet gateway. Access is controlled by IAM permissions, not network rules.
      Global edgeCloudFrontRuns in AWS edge locations worldwide, close to visitors. It reads the S3 bucket because the bucket policy allows only this distribution, and reaches the load balancer at its public address.

      Optional VPC endpoints would give the VPC a private path to S3, ECR, Secrets Manager and CloudWatch so that traffic never crosses the internet. They are mainly useful with private subnets and no NAT gateway, and most have an hourly charge. Not needed for this demo.

      Why there is a load balancer with only one API task

      With one API task the load balancer spreads nothing. Its job here is to give CloudFront one name that never changes, while the API's address changes every time ECS starts a new task. Addresses below are illustrative.

      WhenAPI task addressWhat CloudFront points at
      Monday, first deploy10.20.0.37 (public 3.91.44.12)acquireiq-1234567890.us-east-1.elb.amazonaws.com
      Wednesday, after a crash or new deploy10.20.1.112 (public 54.210.8.77). The old address is gone.The same load balancer name. Nothing to update.

      Who does what

      WhoDoes whatConfigured by
      AWS FargateGives each new API task a new IP address. Nobody picks it.Automatic
      ECS serviceAdds a new task's IP to the load balancer's target list when it starts, and removes the old IP when that task stops.load_balancer block in aws_ecs_service.backend
      Load balancerSends each request to whichever listed IP is passing health checks. It never changes any IP itself, and its own name stays fixed.aws_lb, aws_lb_target_group
      CloudFrontAlways sends API calls to the load balancer's fixed name.domain_name = aws_lb.main.dns_name

      Without a load balancer, CloudFront would point straight at the API's IP, and every crash or deploy would break the app until CloudFront was updated by hand. The load balancer also gives health checks and deploys without downtime. Its classic job, spreading load across several copies, starts automatically if desired_count is raised above 1.
